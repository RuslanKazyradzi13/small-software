# Security

small puts internal apps on the public internet and promises that only the people you list can open them. This page
says exactly what that promise covers, what it does not, and how it is tested. If you find a gap, please report it
privately (below).

## Reporting a vulnerability

Please **do not open a public issue.** Report privately through GitHub: the repository's **Security** tab →
**Report a vulnerability**. Include steps to reproduce and the affected component (`small-cli`, `magic_link.py` or
`magic-link.js`).

You will get an answer within 7 days. Once a fix is released, the report can be credited in the changelog.

| Version | Supported |
|---|---|
| 0.8.x | yes |
| < 0.8 | no — please upgrade (`pip install -U small-software`, then copy the new `magic_link.py` / `magic-link.js` into your app) |

## Threat model

### What is protected

An app deployed with small runs on Railway at a public HTTPS address. Every request passes through `magic-link`
(`magic_link.py` for Python, `magic-link.js` for Node.js, `MagicLinkGate` for Streamlit) **inside the app process**,
before the app's own code. A request gets through only with a valid session of an address on the access list
(`ACCESS_EMAILS`) or a cookie derived from a current invite token (`ACCESS_TOKEN`). Everything else — pages, API,
`/docs`, websockets — gets a sign-in page or is closed. **Deny by default.**

### What we trust

- **Railway**: hosting, TLS termination, the storage of environment variables (secrets live there), logs.
- **Your computer and your Railway account**: the `RAILWAY_API_TOKEN` can change anything about your apps.
- **Google and Microsoft**, for the addresses they vouch for (see below), and **the admins of your Microsoft tenant**.
- **The mailbox**: for email sign-in links, whoever reads the inbox is treated as the owner of the address.
- **The app's own code**: magic-link shares the process with it. A bug in the app (for example, rendering untrusted
  HTML) can undermine it.

### Threats and defenses

| Threat | Defense |
|---|---|
| A stranger opens the URL, or calls the API directly | No valid session, no access: a 403 sign-in page. ASGI websockets are closed before `accept`. |
| Forging a session or a sign-in link | HMAC-SHA256 with `SESSION_SECRET` (generated by small), constant-time comparison, expiry inside the signed data. Each purpose (sign-in link, session, sign-on state, sign-out token) has its own key context: one can't be passed off as another. Changing the secret ends all sessions. |
| A former colleague keeps a session | Every request re-checks the access list: `small access revoke` ends the session at the next restart (small restarts the app). The revocation time also goes to `SESSIONS_REVOKED`, so re-adding the address later does not bring old sessions back. |
| A lost laptop | `small access signout ivan@company.com` (owner) or **Sign out on all devices** (the person, with a volume): every session of that address issued before now stops working; access itself stays. |
| A forwarded or intercepted sign-in email | The link works for 15 minutes, once, only for an address that is still on the list. Opening it shows a **Sign in** button: mail scanners that open links do not sign anyone in or burn the link. |
| Re-using a spent sign-in link after a restart | Used links are recorded in SQLite on the app's volume (`small volume add`), shared by all worker processes. Without a volume see *Limitations*. |
| Redirecting sign-in links to an attacker's domain (`Host` header poisoning) | Links and sign-on redirect addresses are built from `PUBLIC_URL` / `RAILWAY_PUBLIC_DOMAIN`; the `Host` header is trusted only for `localhost`. |
| Login CSRF / session fixation in "Sign in with Google/Microsoft" | Authorization code flow with PKCE (S256), a `state` tied to the browser by a signed `HttpOnly` cookie, a `nonce` checked in the ID token, and each answer accepted once. |
| A forged ID token, or one issued to another app | The ID token comes straight from the provider's token endpoint over TLS, in exchange for our client secret (OpenID Connect Core 3.1.3.7 allows TLS in place of the signature check here). Checked: `aud` (and `azp`), `exp`/`iat` with 5 minutes of clock leeway, `nonce`, `iss`. |
| Claiming someone's address through an identity provider ("nOAuth", personal accounts) | **Google:** the address must be verified, and either a Gmail address or part of a Google Workspace organization (`hd`); a personal Google account registered with a company address is refused — whoever made it may have lost that mailbox long ago. **Microsoft:** only members of your one tenant (`iss` and `tid` must match, guests from elsewhere are refused); the address is the sign-in name (UPN), whose domain your tenant has verified. Tokens of every other tenant are refused. |
| Finding out who is on the list | Email sign-in gives the same answer for known and unknown addresses. Single sign-on tells "no access" only to the person who has just proven the address is theirs. |
| Mail bombing, brute force | At most 3 sign-in emails per address and 10 per IP in 15 minutes (shared across workers with a volume). |
| Open redirects | Redirects go to the app's own paths only; leading slashes are collapsed. |
| Clickjacking, injected scripts, cached pages | Sign-in pages send `X-Frame-Options: DENY` and `Content-Security-Policy: default-src 'none'; form-action 'self'; frame-ancestors 'none'`, contain no scripts, and are `Cache-Control: no-store`, `Referrer-Policy: no-referrer`. |
| Secrets in logs, forged log lines | Tokens, links, codes, client secrets and API keys are never logged; the templates mask `token`, `t`, `code` and `state` in access logs. Sign-ins and requests are logged as one JSON object per line, so a visitor can't forge entries. |
| The local dashboard reached from other sites or machines | `small dashboard` listens on `127.0.0.1` only, checks `Host`, `Origin` and `Sec-Fetch-Site`, needs a per-run key on every change, and can't be framed. |

### Limitations — what small does not protect against

- **People you let in.** Anyone on the list, anyone who controls a listed mailbox or account, and anyone holding a
  personal invite link (it is a bearer token, like a password) gets in until you revoke them.
- **A compromised Railway account, Railway itself, or your computer.**
- **The app's own vulnerabilities.** magic-link guards the door, not the app behind it. In the Streamlit template the
  session cookie is written by JavaScript, so it is not `HttpOnly`: never render untrusted HTML there.
- **No volume, no memory.** Without `small volume add`, used sign-in links, rate limits and "sign out on all devices"
  live in the process memory. After a restart, someone who already has a used link could use it again within its 15
  minutes; the button is not offered in this mode. `SESSIONS_REVOKED` (owner sign-outs and revocations) does not need a
  volume.
- **Sessions are bearer cookies** for 30 days, not bound to a device or IP.
- **Node.js websockets.** `magic-link.js` guards HTTP requests; a websocket upgrade (`server.on('upgrade')`) does not
  pass through it, so an app that accepts websockets must check the session there itself.
- **Microsoft sign-in names are set by your tenant's admins.** Renaming a user changes which address signs in.
- **Denial of service** is left to Railway's edge; small adds only the email limits.
- **The access log** (`small access log`) is Railway's log: it is kept as long as your Railway plan keeps logs.
- **No independent audit yet.** The design and the tests below are public; reviews are welcome.

## How it is tested

- `magic_link.py`: 97 tests, `magic-link.js`: 31 tests, `small-cli`: 180 tests, run by GitHub Actions on Linux,
  macOS and Windows, with the Streamlit and FastAPI templates on the real frameworks.
- Sign-on is tested against a local OpenID provider: tampered `aud`, `azp`, `exp`, `iat`, `nonce` and `iss`; tokens of
  another tenant; guests; personal Google accounts with a company address; a `state` from another browser; replayed
  answers; provider errors; the code exchange with PKCE.
- Sessions and links: forged and cross-purpose signatures, expiry, revocation, rotation of the secret, revocation by
  time, a link spent once under concurrency and across "restarts" and worker processes (SQLite).

## Scope

In scope: bypassing sign-in (single sign-on, email links, invite links), forging or replaying sessions, links or
sign-on answers, accepting an address the provider doesn't vouch for, leaking tokens, links, codes or secrets into
logs or output, redirecting sign-in to another host, the local dashboard being reachable from other machines or sites.

Out of scope: issues in Railway, Google or Microsoft themselves, and findings that need access to the owner's computer
or Railway account.
